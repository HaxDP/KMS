## 1

```mermaid
graph LR
  U[Клієнт] -->|443 HTTPS| F[Фронтенд]
  F -->|8080| A[API]
  A -->|5432| D[(База даних)]
```

те саме у вигляді схеми з портами і сегментами

```
Клієнт --443 HTTPS--> [Фронтенд | публічний сегмент] --8080--> [API | приватний сегмент] --5432--> [База даних | приватний сегмент]
```

| сервіс | сегмент | порт |
|---|---|---|
| фронтенд | публічний | 443 назовні, 8080 до API |
| API | приватний | 8080 від фронтенду, 5432 до бази |
| база даних | приватний | 5432 від API |

назовні відкритий лише порт 443, порти 8080 і 5432 назовні не опубліковано

## 2

обрано bridge, а саме користувацький bridge, і краще дві мережі: публічну для фронтенду і приватну з параметром internal для API та бази

сервіси знаходять один одного за іменем через вбудований DNS Docker, тому фронтенд звертається до api, а API до db, без жорстко прописаних IP-адрес

режим host не обрано, бо контейнери використовували б мережу самого вузла без ізоляції, порти могли б конфліктувати, а база стала б доступна на інтерфейсах вузла

режим overlay не обрано, бо він потрібен для з'єднання контейнерів на різних вузлах кластера і вимагає оркестратора, а тут усі три сервіси працюють на одному вузлі

## 3

| сервіс | дозволений вхідний порт | дозволене джерело |
|---|---|---|
| фронтенд | 443/tcp | інтернет, це єдина публічна точка входу |
| API | 8080/tcp | лише сервіс фронтенд у приватній мережі |
| база даних | 5432/tcp | лише сервіс API у приватній мережі |

порт 80 назовні закритий, бо за вимогою відкритий лише HTTPS

## 4

метрики

затримка відповіді, наприклад p95 часу відповіді API

частка помилок, тобто відсоток відповідей зі статусом 5xx

healthcheck, тобто стан перевірки кожного контейнера

використання ресурсів, тобто CPU і пам'ять контейнерів

кількість з'єднань API з базою даних

порядок діагностики від найшвидшої перевірки до найглибшої

1. перевірити резолв імені і доступність порту, наприклад nslookup api і nc -zv api 8080 з контейнера фронтенду

2. перевірити healthcheck і метрики, тобто стан контейнерів, частку помилок, затримку і використання ресурсів

3. дивитись журнали контейнерів і мережеві правила, групи безпеки та маршрутизацію між сегментами
