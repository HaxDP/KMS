## 1

частка послідовного коду f = 0,25, паралельна частка 0,75

формула S = 1 / f + 1 - f / p

p = 4 - S = 1 / 0,25 + 0,75 / 4 = 1 / 0,25 + 0,1875 = 1 / 0,4375 = 2,29

p = 8 - S = 1 / 0,25 + 0,75 / 8 = 1 / 0,25 + 0,09375 = 1 / 0,34375 = 2,91

p = 16 - S = 1 / 0,25 + 0,75 / 16 = 1 / 0,25 + 0,046875 = 1 / 0,296875 = 3,37

| процесорів | прискорення S |
|---|---|
| 4 | 2,29 |
| 8 | 2,91 |
| 16 | 3,37 |
| нескінченність | 1 / 0,25 = 4 |

перехід з 4 до 8 ядер дає лише +0,62, а з 8 до 16 лише +0,46, при тому що апаратури стає вдвічі більше

висновок - далі нарощувати кількість ядер сенсу майже немає, бо максимум дорівнює 4 і задається послідовною часткою 25 відсотків, а не кількістю ядер

## 2

```
ADD R1, R2, R3   ; R1 = R2 + R3
SUB R4, R1, R5   ; R4 = R1 - R5
```

це конфлікт за даними

команда SUB читає регістр R1 на стадії декодування, а команда ADD записує його в регістровий файл лише на стадії запису результату, тобто на два такти пізніше

конвеєр уже завантажив SUB і вона дійшла до декодування, коли R1 ще не готовий, тому без пересилання даних або зупинки SUB прочитала б старе значення R1

## 3

```
if (x > 0) {
    y = 1;
} else {
    y = 2;
}
```

на асемблері це умовний перехід, наприклад BLE X, 0, else

результат порівняння відомий лише тоді, коли команда переходу виконана, а конвеєр уже вибрав наступні команди

процесор не знає з якої гілки брати команди, тому або чекає, або передбачає перехід

якщо передбачення хибне, вже вибрані команди треба відкинути, а конвеєр очищується, і втрачаються такти, це і є конфлікт за керуванням
